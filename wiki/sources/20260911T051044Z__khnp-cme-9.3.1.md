## N1. tester-backend pom 임시 오버라이드의 자가치유 sed 가 CRLF pom 줄끝을 LF 로 통째 바꿈 (한 세션 2회)

**priority**: 높음

**문제(증상)**
- 1회차(주석 정리 변경검증, 6클래스 107건): 테스트 후 `git status` 에 `tocFramework/pom.xml` 이 M. `git diff --ignore-cr-at-eol` 은 빈 결과 = 줄끝만 바뀜. tester 가 `git checkout -- tocFramework/pom.xml` 로 원복했다 — `tester-backend.md:61·72` 가 **금지**한 방식이다. 이번엔 미커밋 pom 변경이 없어 손실은 없었다.
- 2회차(후속 3클래스 39건): orchestrator 가 위임 프롬프트에 "git checkout 금지, 오버라이드 전 `cp pom pom.harnessbak` 사본을 trap 에서 `mv` 로 원복"을 **명시 주입했는데도 재발**. tester 보고 원문: "self-heal 분기(harnessbak 없을 때 무조건 sed)가 백업 뜨기 **전에** 실행되어 CRLF→LF 전체 손상 … `git checkout` 대신 `git show HEAD:tocFramework/pom.xml > tocFramework/pom.xml` 로 원본 바이트(CRLF) 복원".

**추정 원인** (소스 확인)
- `tester-backend.md:58-63` 자가치유 블록: `.harnessbak` 이 없으면 `sed -i 's#<skipTests>false</skipTests>#<skipTests>true</skipTests>#g' "$POM"` 를 **조건 없이** 실행한다. 치환할 줄이 없어도 Git Bash(msys) `sed -i` 는 파일을 다시 쓰면서 CR 을 떼어낸다(추정 — 2회 실측 결과와 일치).
- `tocFramework/pom.xml` 은 저장소 자체가 CRLF 다(`git ls-files --eol` → `i/crlf w/crlf attr/-text`). `tocAdminServer/pom.xml` 은 `i/lf` 라 같은 sed 가 무해했다 — **CRLF pom 에서만 드러나는** 결함이다.
- 자가치유 sed 는 `cp "$POM" "$POM.harnessbak"`(:65) **이전**이라, 이후 trap 이 되돌리는 백업이 이미 손상본이다. :67 sed(백업 후)도 CR 을 떼지만 trap 이 백업으로 되돌려 무해하다.
- :74 사후 확인(`git status --porcelain pom.xml`)은 제대로 잡았다. 그러나 원복 수단이 md 에 `mv harnessbak` 뿐이라 백업이 손상본이면 **쓸 수단이 없어** tester 가 금지된 git checkout 으로 흘렀다. 금지만 있고 대안이 없는 규칙이다.

**제안 개선 방향**
1. `:62` 자가치유 sed 를 `grep -q '<skipTests>false</skipTests>' "$POM" && sed …` 로 조건화한다. 2회차 tester 가 `tocAdminServer/pom.xml` 에 즉흥 적용했고 무해했다.
2. sed 두 곳을 CR 보존 방식으로 바꾼다: `sed -b -i …` (⚠ **미검증** — msys GNU sed `-b/--binary` 가 CRLF 를 보존하는지 CRLF pom 에 1회 실측 필요) 또는 python bytes 치환.
3. `:74` 원복 실패 절차에 "`git diff --ignore-cr-at-eol --quiet -- <pom>` 이 참(= 내용 변경 없음, 줄끝만 손상)일 때에 한해 `git show HEAD:<pom> > <pom>` 허용"을 명문화한다. 내용 변경이 있으면 지금처럼 금지한다(developer 미커밋 변경 보호 취지 유지).
4. `tester-runtime.md` 등 같은 절차를 복제한 md 가 있으면 동기화한다.

**근거**
- 이 세션 tester-backend 보고 2건(위 인용)
- 실측: `git ls-files --eol -- tocFramework/pom.xml tocAdminServer/pom.xml` → `i/crlf w/crlf` / `i/lf w/lf`
- 관련 파일: `.claude/agents/tester/tester-backend.md:45-74`, `.claude/agents/orchestrator.md ## 핵심 규칙` "JUnit 실행: … 자가치유 = harnessbak 복원 또는 skipTests 줄만 sed 원복"

## N2. Git Bash 도구 환경에서 `grep -c $'\r$'` 가 줄끝 판정에 no-op — 측정식이 참/거짓을 못 가름

**priority**: 중간

**문제(증상)**
- orchestrator 가 JSP 편집 반영을 확인하며 `printf 'lines=%s crlf=%s' "$(wc -l < $J)" "$(grep -c $'\r$' $J)"` → `lines=129 crlf=129` 를 받고 사용자에게 "129줄 모두 CRLF 유지"라고 보고했다. 같은 전제("JSP 는 CRLF")를 tester 위임에도 주입했다.
- tester-backend 가 실측으로 반박(LF). tester-frontend 는 같은 오판("CRLF 100%")을 보고했다.
- 재측정: LF 로 확정된 파일(`tocAdminServer/pom.xml`, `git ls-files --eol` = `i/lf w/lf`)에 같은 식 → `grep-crlf=250` = 전체 줄 수. `tr -cd '\r' < attachtransferlog.jsp | wc -c` = **0**. `git ls-files --eol` 은 JSP 를 `i/lf w/lf` 로 표시.
- 파일 손상은 없었다. 틀린 사실이 사용자 보고와 위임 전제로 퍼진 것이 비용이다(정정 보고 1회).

**추정 원인**
- 미확인. msys grep 의 텍스트 모드 CR 처리 또는 도구 레이어의 `$'…'` 해석 중 하나로 추정. 원인과 무관하게 **이 측정식은 CR 이 있든 없든 같은 값을 낸다.**

**제안 개선 방향**
1. wiki gotcha 1페이지: 증상 → 원인(미확인) → 회피(`git ls-files --eol` / `tr -cd '\r' < f | wc -c` / python bytes 로 CR 개수). 기존 `jq-crlf-stdout-windows.md` 와 "같은 표면(Windows CRLF)·다른 원인" 클러스터로 상호 링크.
2. `orchestrator.md §0④` 의 "인코딩·이스케이프·바이트 수준 검증은 파이프를 경유하지 않는다" 항목에 줄끝 판정 1줄을 추가한다. 기존 항목은 "파이프가 결과를 오염"만 다루고, **측정식 자체가 no-op** 인 경우는 없다.
3. (선택) 판정용 측정식은 **답을 아는 반례 1개에 먼저 돌려** 참/거짓을 가르는지 확인한다. 이번엔 LF 확정 파일 1개로 30초 만에 드러났다.

**근거**
- 이 세션 명령과 출력(위 수치), tester-backend 2회차 보고 "지시된 CRLF 전제가 사실과 다름"
- 관련 파일: `.claude/agents/orchestrator.md §0④`, `.claude/wiki/jq-crlf-stdout-windows.md`
- gstack learnings `gitbash-grep-cr-count-noop` (confidence 10)
