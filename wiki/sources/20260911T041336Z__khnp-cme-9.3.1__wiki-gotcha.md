# wiki gotcha 스텁 — 공유 `~/.m2` 로컬 저장소도 워크트리 분리로 안 풀린다

**제안 형태**: 기존 `shared-test-db-worktree-noop.md` 의 교훈("자원 경합은 층이 있다 — 파일 < 빌드 산출 < 공유 상태 저장소")에 **두 번째 사례**로 확장하는 것을 권장. 제목을 "공유 상태 저장소(테스트 DB · `~/.m2`)는 워크트리 분리로 안 풀린다"로 일반화하거나, 새 페이지를 만들고 양방향 `[[링크]]`.

**증상**
- 다중 모듈 Maven 프로젝트에서 상위 모듈을 `install` 한 직후 하위 모듈 빌드가 **이번 변경과 무관한 클래스**를 못 찾는다(`cannot find symbol`). 방금 install 한 jar 를 열어보면 클래스 구성이 다르다.
- 반대로, 내가 install 한 뒤 **다른 워크트리**에서 하위 모듈만 빌드하면 그쪽이 깨진다(내 브랜치에서 지운·이름 바꾼 메서드를 그쪽 코드가 부름).

**진짜 원인**
- `~/.m2/repository` 는 **머신 전역 하나**다. 워크트리는 파일시스템(소스·`target/`)만 나눈다.
- 고정 버전(비-SNAPSHOT) 같은 GAV 로 install 하면 **마지막에 쓴 쪽이 이긴다**. 워크트리 여러 개가 같은 `groupId:artifactId:version` 을 쓰면 서로의 jar 를 조용히 덮는다.
- 실측(khnp cme-9.3.1): 워크트리 5개가 `com.crinity:crinity-toc-core:9.3.1` 공유. 10:46 install → 10:48 다른 세션 install 로 954 classes 짜리로 교체 → 하위 모듈 컴파일 실패. 재install 후 950 classes 확인하고 **곧바로** 하위 빌드해 해소.

**회피**
- 상위 모듈 install 직후 **이번 변경의 식별 표지(새 클래스·새 메서드)가 jar 에 있는지 확인하고 즉시** 하위 모듈을 빌드한다(`jar tf <jar> | grep <클래스>`, 또는 클래스 파일에서 메서드명 문자열 확인). 사이에 다른 작업을 끼우지 않는다.
- 하위 모듈 빌드가 **무관한 클래스 부재**로 깨지면 소스 결함보다 공유 jar 덮어쓰기를 먼저 의심한다.
- install 을 했으면 "공유 jar 가 이 브랜치 버전이 됐다"를 기록·통지한다 — 같은 GAV 를 쓰는 다른 워크트리는 **자기 상위 모듈을 먼저 install** 해야 한다.
- 워크트리별 `-Dmaven.repo.local` 격리는 원리상 답이지만 오프라인(`-o`) 의존성 사본 비용이 커서 미검증.

**교훈**
- 테스트 DB 와 같은 층이다: **공유 상태 저장소는 워크트리로 안 풀린다.** 차이는 DB 는 "순차만 답"이고 `~/.m2` 는 "install 직후 확인 + 즉시 사용"으로 창을 좁힐 수 있다는 점.
- 착수 게이트(toplevel/branch 확인)는 **잘못된 클론** 사고는 막지만 **정상 세션끼리의 동시 실행**은 못 막는다.
