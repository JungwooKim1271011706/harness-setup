# Co-Plan — 함께 만드는 계획

AI 혼자 계획서를 써서 가져오는 대신, 유저와 단계별로 대화하며 함께 설계한다.
목표는 planner에게 전달할 합의된 spec을 만드는 것이다.

## 호출 시 받는 컨텍스트

오케스트레이터가 아래 정보를 전달한다:

- **feature**: 만들려는 기능 설명 (1~2문장)
- **domain**: `frontend` | `backend` | `mixed`
- **context**: 관련 기존 코드/API 정보 (선택)

## OOP 설계 원칙 (Step 4~5 전 적용)

```
OOP 5단계 정렬 순서:
  ① 역할·데이터 정의 → ② 책임 분배 → ③ 메시지(인터페이스) 설계
  → ④ 협력 관계 확정 → ⑤ 클래스 구조 확정
```

- **RDD(책임 주도 설계)** 적용.
- **정보 전문가 원칙**: 데이터를 가진 객체가 책임을 진다.
- **God 클래스 금지**: 단일 클래스에 책임 집중 금지.
- **⑤단계 시그니처는 public 계약만 freeze** — 내부 private 구현은 developer 자유.

> 이 블록은 v5.4.0까지 orchestrator가 호출마다 **주입**하던 것이다. 스킬이 repo SSOT임이 확인돼(`sync-skills.sh` 동기화 대상은 grill-with-docs뿐) 본문으로 옮겼다. orchestrator가 주입하는 건 이제 **0단계에서 정해지는 rule 경로 한 줄뿐**이다.

## 진행 단계

```
Step 1: 유저 시나리오 (정상 흐름)     [필수 · 합의 루프]
Step 2: 에러/예외 시나리오             [필수 · 합의 루프]
Step 3: API 계약                       [domain=mixed 또는 frontend+backend 연동 시만 · 자동 진행]
Step 4: 클래스 설계                    [필수 · 자동 진행]
Step 5: 메서드 설계                    [필수 · 자동 진행]
```

## 각 Step 진행 방식

**Step 1~2 — 합의 루프** (사용자가 SSOT인 도메인 지식: 어떤 흐름이어야 하나, 실제 어떤 에러가 나나):

```
1. AI가 초안 제시
2. 유저 응답
3. AI 반영/수정
4. 유저 "ㅇㅇ" 또는 "넘어가자" → 다음 Step
```

**Step 3~5 — 자동 진행** (기술 실현 — 뒤에 planner → 설계패널∥codex → 사용자 승인 게이트가 검증하므로 여기서 왕복하지 않는다):

```
1. AI가 초안을 출력하고 **응답 대기 없이** 다음 Step으로 진행 (관망 가능하게 표시는 유지)
2. 유저가 어느 시점이든 개입("잠깐"·수정 지시)하면 그 Step부터 합의 루프로 전환
```

### 출력 형식

```

[Step 1이면: ASCII 흐름도 → 그 아래 단계별 번호 목록]

[Step 3~5] (질문 없이 초안 출력 → 바로 다음 Step)
```


### 초안 작성 기준

- **유저 시나리오**: 현재 흐름 → 변경 후 흐름. **ASCII 흐름도(박스 `┌─┐│└─┘` + 화살표 `──▶ ▼`)를 콘솔에 도식화**한 뒤 단계별 번호 목록을 병기한다 — 유저가 시각적으로 바로 이해하게. 분기(성공/실패·조건)는 화살표 분기로 표현. 터미널서 즉시 읽히게 **ASCII만** 사용(mermaid·excalidraw·파일 생성 금지). 흐름이 단순 선형이면 도식 생략 가능, 유저가 "목록만" 하면 텍스트만.
- **에러 시나리오**: "~가 없으면?", "~가 실패하면?" 형태로 3~5개.
- **API 계약**: 엔드포인트, 요청/응답 shape, 에러 코드. **외부 API 응답을 매핑하는 DTO는 실제 JSON 필드명(snake_case 등)·`@JsonProperty` 매핑을 계약에 명시**하고 "JSON round-trip 테스트 대상"으로 표시한다(목킹만으로 통과하는 필드매핑 통합버그 차단 — tester-design RED 규칙과 연동).
- **클래스 설계**: 새로 만들거나 변경할 클래스/컴포넌트 목록. **신규와 기존수정을 갈라서 쓴다** — 해상도 요구가 다르다.
  - **신규**: 클래스명 + 역할 한 줄.
  - **기존 수정**: 유저가 *수정 범위를 스스로 판정*할 수 있어야 하므로 한 줄로 끝내지 않는다. 항목마다:
    ① **파일 경로** ② **현재 역할** — 이 클래스가 지금 무엇을 책임지고 누구와 협력하나(1~2줄) ③ **이번 변경이 바꾸는 동작** — `현재: … → 변경 후: …` 대조. 유저가 보는 차이로 쓴다(내부 구조 용어만 쓰지 마라) ④ **변경 성격** — `책임 추가` / `기존 분기 변경` / `계약 변경`(계약 변경이면 소비자 영향 1줄).
  - ⚠ **②는 실제 소스를 Read한 근거로 쓴다.** 못 읽었으면 추측으로 채우지 말고 `⚠ 미확인 — 추정` 라벨을 붙인다(orchestrator `§0④ 데이터 전제 검증`의 co-plan판 — 틀린 현재상태 위에 세운 합의는 승인까지 통과한 뒤 구현에서 뒤집힌다).
- **메서드 설계**: 클래스별 핵심 메서드. 여기서도 **신규 / 기존수정**을 가른다.
  - **신규 메서드**: 시그니처 + 역할 한 줄.
  - **기존 메서드 수정**: 유저가 diff를 상상할 수 있을 만큼 낸다. 항목마다:
    ① **`파일:라인 · 메서드 시그니처`** ② **현재 하는 일** 1줄 ③ **삽입·교체 지점** — 어느 조건 분기 안인지 + **앵커 코드 1줄 인용**(라인 번호는 편집으로 밀리므로 번호 단독 금지, 앵커와 함께) ④ **들어갈 소스 스케치** — 시그니처가 아니라 **실제 코드 몇 줄** ⑤ **호출측에서 달라지는 것** 1줄.
  - 스케치는 확정 구현이 아니다(내부 private 구현은 developer 자유 — OOP ⑤단계 원칙). **어디에 무엇이 왜 들어가나**를 보여주는 게 목적이지 코드를 여기서 완성하는 게 아니다.
  - 기존수정 항목이 **6개를 넘으면** 전건 나열 대신 *영향 큰 것 5개 + 나머지는 파일·메서드명만* 으로 줄이고 "나머지 N건 상세 필요하면 말해줘"를 붙인다(출력 폭주 방지).

## Step 건너뛰기

유저가 "skip" 또는 "넘어가" 하면 해당 Step을 건너뛴다(초안 출력 자체를 생략).
단, Step 1(유저 시나리오)와 Step 4(클래스 설계)는 건너뛸 수 없다.
⚠ Step 3~5의 **자동 진행은 스킵이 아니다** — 초안은 출력하되 합의 왕복만 없는 것. 건너뛰기 규칙과 별개.

## 완료 후 처리

모든 Step 합의 완료 후 아래 형식으로 spec을 정리한다:

```
✅ 합의된 spec

## 유저 시나리오
[합의 내용]

## 에러 시나리오
[합의 내용]

## API 계약
[합의 내용 또는 "해당 없음"]

## 클래스 설계
[신규: 목록 + 역할 / 기존수정: 파일 · 현재역할 · 현재→변경후 · 성격]

## 메서드 설계
[신규: 시그니처 + 역할 / 기존수정: 파일:라인 · 시그니처 · 현재 · 삽입지점(앵커) · 소스 스케치 · 호출측 변화]
```

⚠ 기존수정 항목의 **현재 역할·현재 동작**은 planner가 그대로 승계해 계획서 baseline이 된다. `⚠ 미확인 — 추정` 라벨이 남아 있으면 **그 라벨째로** 넘긴다(조용히 확정으로 바꾸지 마라 — 설계패널·승인 게이트가 그 축을 의심할 수 있게).

이 spec을 planner에게 전달하며 "이 spec 기준으로 기술 구현 계획을 작성해줘"라고 지시한다.
오케스트레이터에게: **"co-plan 완료. planner 호출 가능."** 라고 전달한다.
